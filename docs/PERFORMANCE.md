# 性能基线

## 怎么测

```bash
cd backend
python -m app.evals.load_bench --concurrency 1,4,16 --duration 8 --cache off --report perf.json
python -m app.evals.load_bench --database-url postgresql+psycopg://... --workers 4   # PostgreSQL + 多进程
```

脚本会启动一个真实的 uvicorn 服务（离线模型、独立数据库），登录后在每个并发档位下持续调用 `POST /api/chat`，统计每秒请求数（RPS）、延迟分位数和错误率。问题轮流使用 6 个：知识问答、订单查询、物流查询等。

**测的是什么**：离线模型几乎瞬间返回，所以这里测的是**模型以外的平台开销**，包括路由、检索、工具、证据校验、链路写入和数据库。接入真实模型后，一次模型调用通常需要 1–3 秒，会成为延迟的主要部分，下表应该理解为“平台能承受的上限”，而不是线上预测。

## 结果

环境：Apple M1 Max（10 核）、Python 3.12、uvicorn 单进程、SQLite 文件库、离线模型，每档持续 8 秒，错误率均为 0。

| 场景 | 并发 | RPS | p50 | p95 | p99 |
|---|---|---|---|---|---|
| 基线（SQLite 默认配置） | 1 | 94.9 | 10.2ms | 12.4ms | 14.7ms |
| | 4 | 95.5 | 20.1ms | 141.2ms | 260.1ms |
| | 16 | 66.8 | 58.7ms | 651.6ms | 1366.5ms |
| 开启 WAL + busy_timeout | 1 | **143.1** | 6.7ms | 8.8ms | 11.3ms |
| | 4 | **141.6** | 20.9ms | 63.1ms | 123.7ms |
| | 16 | **93.6** | 55.1ms | 402.4ms | 754.3ms |
| WAL + 答案缓存（重复 FAQ） | 1 | 180.2 | 4.7ms | 8.3ms | 9.7ms |
| | 4 | 176.2 | 16.8ms | 51.6ms | 111.2ms |
| | 16 | 109.6 | 39.2ms | 300.7ms | 738.1ms |

## 分析

1. **SQLite 的单写者锁是第一个瓶颈。** 每次对话要写运行记录、多个 span（每个 span 完成后立即提交，以便链路页面实时可见）和消息，一次请求大约提交 8 到 10 次。默认的 rollback journal 模式下，读写会互相阻塞。开启 WAL 后，读不阻塞写，`synchronous=NORMAL` 也减少了 fsync，因此吞吐提升 40%–50%，并发 16 时的 p99 几乎减半（`app/db.py` 中的 `_sqlite_pragmas`）。
2. **单进程加 GIL 是第二个瓶颈。** 并发从 1 增加到 4，吞吐几乎不变：分词、BM25（纯 Python 遍历片段）、证据校验都是 CPU 密集的 Python 代码，同步接口在线程池中运行，多线程无法利用多核。并发 16 时还会出现锁等待和线程切换，吞吐反而下降，尾延迟上升。
3. **答案缓存**跳过了检索和模型调用，在重复 FAQ 场景下吞吐再提高约 25%。

## 优化：分词结果缓存（已采用）

剖析（cProfile，单进程跑 120 次对话）显示，jieba 分词约占每次请求 CPU 的 15%：一次回答会对同样的知识库句子分词好几次（检索、答案抽取、证据校验各一次）。分词对同一段文本、同一份词典是纯函数，所以对 2000 字以内的文本做了 LRU 缓存（4096 条）；整篇文档入库时的长文本不缓存，内存有上界。缓存返回副本，调用方修改列表不会污染缓存。

| 并发（关闭答案缓存，各测两次） | 改动前 RPS | 改动后 RPS | p50 | p99 |
|---|---|---|---|---|
| 1 | 141.1 / 141.2 | **161.5 / 162.8**（+15%） | 6.9 → 6.0ms | 9.8 → 9.7ms，持平 |
| 4 | 136.8 / 138.1 | **157.2 / 158.5**（+15%） | 21.4 → 17.2ms | 117–136 → 133–140ms，在噪声范围内 |
| 16 | 87.1 / 90.1 | **103.4 / 96.6**（+11%） | 59 → 46ms | 863–946 → 749–845ms |

并发 4 的 p99 两组区间有重叠，不宣称改善；吞吐量提升后，单位时间内争抢 SQLite 写锁的请求更多，尾延迟主要还是由写锁决定。

## 优化：检索随知识库规模（已采用）

压测只用了演示知识库（约 30 个片段），看不出检索怎么随规模变化。新增 `python -m app.evals.retrieval_bench`：在临时库里给演示租户加 N 个合成片段（演示知识库的句子重新组合，再加上虚构的商品名，词汇和长度接近真实），测重建索引的时间和每次 `hybrid_search` 的耗时（本机 Apple M1 Max，离线哈希向量，每档 20 次）。

| 片段数 | 改动前 p50 / p95 | 改动后 p50 / p95 | 重建索引 |
|---|---|---|---|
| 1,000 | 19.7 / 20.4ms | **0.6 / 2.4ms** | 0.02 → 0.04s |
| 5,000 | 99.0 / 134.2ms | **2.1 / 4.9ms** | 0.95 → 1.02s |
| 20,000 | 391.5 / 410.5ms | **10.2 / 21.4ms** | 3.6 → 4.0s |
| 50,000 | — | **26.7 / 49.8ms** | 10.5s |

- **原因**：两路召回都在 Python 里逐个片段计算。BM25 对每个片段、每个查询词查一次词频；向量路对每个片段做一次 512 维点积。耗时随片段数线性增长，十万片段时一次检索约 2 秒。
- **改法**：BM25 改为倒排表，查询只访问包含查询词的片段；向量分数改为一次矩阵乘法（numpy，float32 矩阵：2 万 × 512 维约 40MB，原来每个片段一个 Python 浮点数列表，内存是它的好几倍）。
- **结果不变**：新增测试把两种实现放在一起比：BM25 的名次和分数逐位相同（每个片段按同样的顺序累加）；向量分数差在 1e-5 以内、名次相同。唯一的差别是 float32 下接近 0 的分数：原实现会把 1e-9 这样的浮点噪声当作“有相似度”收进候选，现在低于 1e-6 视为不相关。门禁 46/46、检索 hit@1 和 MRR、门槛探针（33/33、16/20）都没有变化。
- **剩下的瓶颈**：任何文档变更后，索引在下一次检索时整体重建（5 万片段约 10 秒，主要是分词），这次检索要等它；每个 worker 各建一份。下一步是增量更新（只对变更的文档分词）或后台重建、先用旧索引服务。片段数到十万级、或换成稠密的真实向量模型后，向量路再换成 pgvector / Milvus 的近似最近邻索引。

## PostgreSQL 与多 worker（GitHub Actions 实测）

本机没有 PostgreSQL，所以在 GitHub Actions 上跑（手动触发的 `Load benchmark` 工作流）：同一台 4 vCPU 的 runner 上依次测 SQLite 单 worker、PostgreSQL 单 worker、PostgreSQL 4 个 worker；每种配置用独立的数据库，测量前先预热 5 秒。压测客户端和服务在同一台机器上，所以多 worker 的结果包含了两者争抢 CPU 的影响。

| 配置（同一次运行，每档 10 秒） | 并发 1 | 并发 4 | 并发 16 |
|---|---|---|---|
| SQLite（WAL），1 worker | 90.8 RPS，p99 15ms | 82.7 RPS，p99 188ms | 76.3 RPS，p99 1299ms |
| PostgreSQL，1 worker | 40.6 RPS，p99 30ms | 49.2 RPS，p99 102ms | 45.1 RPS，p99 470ms |
| PostgreSQL，4 workers | 14.9 RPS，p99 76ms | 50.2 RPS，p99 94ms | **103.6 RPS，p99 222ms** |

- **共享 runner 的绝对数字不可比**：两次运行之间，SQLite 并发 1 分别测得 148 和 91 RPS。只比较同一次运行里的不同配置。
- **PostgreSQL 单请求更慢**：一次请求大约提交 10 次（每个 span 完成即提交），每次都是一次网络往返加 WAL 刷盘，所以单 worker 时吞吐不到 SQLite 的一半。
- **但高并发时更稳**：没有全库单写者锁，并发 16 时 PostgreSQL 单 worker 的 p99（470ms）只有 SQLite（1299ms）的三分之一多一点。
- **多 worker 才能用上多核**：PostgreSQL 4 个 worker 在并发 16 时吞吐是单 worker 的 2.3 倍，p99 再减半，是三种配置里最好的。本机 SQLite 也有同样的趋势：并发 4 时 4 个 worker 比 1 个多 40%（153 → 215 RPS），但 SQLite 的写锁限制了上限。
- **并发 1 时 4 workers 反而慢：时间不在应用里**。CI 上 PostgreSQL 4 workers 在并发 1 时每个请求固定多出约 41ms，预热和独立数据库都没消除，本机（macOS、SQLite）也复现不了。为了定位，给每个响应加了 `Server-Timing: app;dur=…`（应用内耗时），压测同时报告客户端和应用内的分位数。第三次运行的结果：

  | 配置（并发 1） | 客户端 p50 | 应用内 p50 |
  |---|---|---|
  | PostgreSQL，1 worker | 15.1ms | 14.4ms |
  | PostgreSQL，4 workers | 57.1ms | 16.1ms |

  应用内耗时两者几乎一样，多出的约 41ms 全部在应用之外：客户端与 uvicorn 多进程模式之间的连接处理。每个请求固定约 40ms，是 Nagle 算法和延迟 ACK 相遇的典型特征，但这一点还没有用抓包证实。生产流量会先经过反向代理（连接池、长连接），所以这个数字要在代理后面重测，而不是在应用里调。

- **结论**：生产部署用 PostgreSQL 加多 worker。只去掉刷盘等待的“异步提交”实测没有收益；减少往返次数的“批量写链路”实测提升 39%–47%，已经是 PostgreSQL 上的默认做法（见下方）。

## 优化：PostgreSQL 上批量写链路（已采用）

异步提交实验说明瓶颈不在 WAL 刷盘，于是先数清楚一次请求到底发了多少条 SQL：用 SQLAlchemy 事件监听统计，一次对话 23.3 条语句、9.3 次提交，加上 psycopg 每个事务的隐式 BEGIN，在 PostgreSQL 上大约 40 次往返，大部分来自“每个 span 完成即提交”（以及随之更新运行记录的 token 用量）。

改法：PostgreSQL 上链路先写进内存，在运行自己的提交点（结束、暂停审批、出错）一次交给数据库；每次请求的提交从 9.3 次降到 3.0 次。SQLite 仍然逐个提交，因为前面的实验证明合并写入在 SQLite 上会让 p99 变差。代价：PostgreSQL 上要等运行结束才能在链路页面看到这次运行的 span。

同一次 CI 运行内对比（PostgreSQL，1 worker）：

| 链路写入方式 | 并发 1 | 并发 4 | 并发 16 | 应用内 p50（并发 1） | p99（并发 16） |
|---|---|---|---|---|---|
| 逐个提交 | 36.5 RPS | 45.0 RPS | 40.4 RPS | 25.5ms | 528ms |
| 批量写入 | **53.5 RPS** | **62.5 RPS** | **57.2 RPS** | 17.1ms | 393ms |

吞吐提升 39%–47%。同一次运行里，PostgreSQL 4 workers 在并发 16 时 129.7 RPS、p99 193ms。

**CI 抓到的一个 bug**：第一版推送后，CI 的 PostgreSQL job 失败了 4 个测试。运行结束时要根据本次用过的工具判断状态（是否转人工）和能否写入答案缓存，而工具列表是从数据库里的 span 查出来的；批量模式下这时 span 还在内存里，查到的是空列表。修复是在查询前先把缓冲交给会话。为了不再只靠 PostgreSQL job 发现这类问题，SQLite job 也用批量模式把整套测试再跑一遍（`LOOPDESK_TEST_TRACE_WRITES=buffered`）。

## 实验：PostgreSQL 上链路 span 异步提交（未采用）

假设：PostgreSQL 单请求慢在约 10 次提交都要等 WAL 刷盘，而其中大部分只写链路 span。于是让 span 的提交使用 `SET LOCAL synchronous_commit TO OFF`（业务写入仍同步提交），预期单 worker 吞吐明显上升。

在同一次 CI 运行里对比（PostgreSQL，1 worker，每档 10 秒，先预热）：

| span 提交方式 | 并发 1 | 并发 4 | 并发 16 | 应用内 p50（并发 1） |
|---|---|---|---|---|
| 同步（默认） | 38.3 RPS | 46.2 RPS | 41.3 RPS | 24.5ms |
| 异步 | 37.0 RPS | 43.5 RPS | 39.4 RPS | 25.4ms |

没有任何提升（差异在噪声范围内，略低）。这说明在这套环境里，PostgreSQL 的单请求开销不在 WAL 刷盘，而更可能在每条语句的网络往返和同一台 4 vCPU 机器上的 CPU 争抢。异步提交用持久性换性能，没有收益就不该保留，所以代码已回退。下一步要先用 `pg_stat_statements` 或服务端分段计时找出真正的大头，再决定优化方向。

## 实验：合并 span 写入（未采用）

假设：每个 span 单独提交是剩下的主要开销，把提交合并成“至多每 0.25 秒一次，并在执行工具前提交一次”应该会更快。

| 方案（关闭缓存，各测两次） | 并发 4：RPS | 并发 4：p99 | 并发 16：RPS | 并发 16：p99 |
|---|---|---|---|---|
| 只开 WAL（当前方案） | 143–145 | 118–135ms | 97–99 | 845–923ms |
| 合并 span 写入 | 154–155 | 190–199ms | 96–101 | 942–950ms |

吞吐提高约 7%，但**并发 4 时 p99 稳定变差约 50%**，并发 16 的吞吐没有改善。原因是合并后单次提交的写入量更大，持锁时间更长，排在后面的请求等待得更久。客服场景更看重尾延迟，而且合并写入还会让链路页面的实时性变差，所以**没有采用**。合并写入只有在换成 PostgreSQL（行级锁，没有全库单写者）之后才值得重新评估。

## 下一步（按收益排序）

| 改动 | 预期效果 |
|---|---|
| 检索索引增量更新，或后台重建时先用旧索引服务 | 现在任何文档变更都会让下一次检索等待整体重建（5 万片段约 10 秒） |
| 链路写入改为异步队列（批量写入独立的存储） | 把链路写入移出请求路径。在 SQLite 上要小心：去掉每个 span 的提交后，请求事务里对 Run 的更新会一直持有写锁直到运行结束，等于把模型调用也包进了锁里；应该在 PostgreSQL 上做，或者 Run 的更新也一并异步化 |
| 接入真实模型后改为异步 IO（async httpx + 异步数据库） | 等待模型返回期间线程处于空闲，异步化后单进程可以同时挂起的对话数从线程池大小（约 40）提高到上千 |
| 向量检索换成 pgvector 或 Milvus，BM25 换成搜索引擎 | 倒排表和矩阵乘法之后，检索在 5 万片段时约 27ms；十万级以上、稠密向量时再换近似最近邻索引 |

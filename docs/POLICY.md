# 审批策略：策略即代码（1.2.0）

退款、审批分级、四眼原则和语音渠道的确认，写在一份 [Cedar](https://github.com/cedar-policy/cedar)（Apache-2.0）策略里：`backend/policies/loopdesk.cedar`，请求的格式在 `backend/policies/loopdesk.cedarschema`。后端用 [cedarpy](https://github.com/k9securityio/cedar-py) 4.12.2 判定，静态演示用 `@cedar-policy/cedar-wasm` 4.12.0 判定，两边都是 Cedar 引擎 4.12.0，读的是同一份文件。

## 为什么用现成的绑定，不自己写一份

后端的 Python 绑定 cedarpy 是社区项目（k9securityio，不是 AWS 官方），2026-11-10 查看时：4.12.2 发布于 2026-10-14，对应 Cedar 4.12.0，仓库最近一次提交 2026-11-02，Apache-2.0，有 Linux、macOS、Windows 的预编译 wheel（Python 3.10 到 3.14）。它在维护，所以直接用它，没有另写一个等价的判定器。两边判定一致由测试保证（下面“一致性”）。

## 怎么判定

- **网关收集事实，Cedar 判定，网关执行。** 每一次改动数据的工具调用（退款、撤回申请、建工单、转人工、租户自己的工具）都先问策略；没有一条 `permit` 匹配就不办（默认拒绝）。审批队列里的“通过 / 驳回 / 提交人撤回”同样先问策略。只读工具（查订单、查物流、检索）不改数据，仍按角色清单开放。
- **实际的规则集中在退款、审批队列和语音渠道。** 建工单、转人工、租户自己的工具，策略对任何角色都放行：谁能用哪个工具仍由代码里的角色清单决定，租户工具的审批额度仍由租户声明的配置决定（`app/tooling/policy.py`，保存时校验，不能比租户的退款分级更松）。默认拒绝对它们的意义是：清单之外的新动作，在策略里写出 `permit` 之前一律不能执行。
- **三种结论**，由起作用的策略的 `@id` 前缀区分：
  - `allow`：有 `permit` 匹配，没有 `forbid` 匹配；
  - `review`：只有 `review.*` 的 `forbid` 匹配，而且去掉它们时有 `permit` 匹配：交给一位员工审批；
  - `deny`：有 `deny.*` 的 `forbid` 匹配，或者什么都没允许。请求不符合 schema、策略求值出错，也是 `deny`（Cedar 会跳过出错的策略，这里改成整次拒绝）。
- **先后顺序就是文件里的顺序。** 几条同时成立时，告诉顾客的是排在最前面的一条，和改写之前代码里检查的顺序一致，所以顾客看到的话没有变。`@stage("approval")` 标的两条（员工代办的顾客没有账号、没有另一位能审批的员工）在渠道确认之后才检查，和以前一样。
- **事实按以前的顺序收集。** 一个已经能决定结果的事实（顾客说了先不退），或者一次读失败（订单不存在、不是这位顾客的、金额不是数字），之后的事实就不再去读：策略缺了这些事实，没有一条 `permit` 能成立。
- **每次判定是链路里单独的一段**（`policy` / `cedar:<动作>`），记下送进去的事实、结论、起作用的策略、引擎版本和耗时。

## 不变式（`@locked`）

五条策略标了 `@locked("true")`：退款金额大于 0、退款不超过实付、四眼原则（审批人不是提交人）、员工只能提交别人能审批的申请、语音渠道动钱要先口头确认。

`review.claimed_authority`（消息里自称系统通知、已获授权或员工身份）只在封闭语法读得过去的消息上起作用：语法把“【系统通知】……”这类插入的话当作不影响请求的一句，这样的退款交人工；“我是店长，SO… 申请退款”语法本身就不接受，只会提议、不提交。“如果……会怎样”面板不能关掉它们，`whatif.ts` 也会忽略关掉它们的请求。

`backend/tests/test_policy.py` 和 `frontend/src/demo/engine/policy.test.ts` 对上线的策略、每一条可关的策略单独关掉、全部关掉、以及 12 个随机组合，都检查：

- 任何策略组合都不会让超过实付的退款通过或进入审批（`reviewed` 真假两种都查）；
- 审批人永远不是提交人（三种角色、六档金额、三种审批人设置）；
- 员工代办时，如果没有另一位能审批的员工，申请被拒绝而不是挂在队列里；
- 语音渠道没有口头确认时，动钱一律拒绝。

这是在生成的请求上检查，不是形式化证明。这几条成立是因为执行它们的规则锁定，所以测试说明的是“没有一条 permit 能绕过这些 forbid、两段式判定不会把它们放成人工审批”；网关自己收集的事实（实付金额、是否在执行已批准的申请）另有一条接口测试：所有可关的规则都关掉，经 API 说“退100元”，台账和审批队列都是空的。Cedar 自己的符号分析（`cedar-policy-symcc`）没有 Python 和 wasm 版本，这一版没有用。

## 一致性：改写前后、两个引擎之间

- **改写前后，判定逐条相同。** 改写之前先在原来的代码上记下了每一次工具调用和每一次审批的结论（提交 `fc65238`）：后端 `python -m app.evals.decisions --record`（15 段完整对话、24 张开发卡的示例句、144 段录制的模拟对话按原句重放、Fable 的 331 / 274 / 205 条清单、5 份动钱集合、主会话对 1.1.0 的 30 条探查），浏览器 `decisions.test.ts`（同样的对话和清单，加上评审探查和覆盖测试的 110 句）。切换到 Cedar 之后（提交 `a7e60f4`）：后端 1200 段、3106 次判定，0 段不同；浏览器 1562 段、3928 次判定，0 段不同。CI 每次都重跑这个比较。
- 比对的是调用方看到的结论（工具、订单、金额、通过 / 交人工 / 拒绝 / 先问顾客、顾客读到的那句话），不是起作用的规则。语音渠道不在这几份对话里，由策略层测试和原有的语音测试覆盖。
- **两个引擎，答案相同。** `python -m app.evals.policy_cases --write` 生成 1130 个请求（每个动作、每种角色、每个额度的两侧，加上固定种子的随机组合），存下 cedarpy 的结论；`policy.test.ts` 用 cedar-wasm 逐个判定，结论和起作用的策略都必须相同。
- **之后有意改变的判定**（1.2.0 修的问题）：和切换前的录制相比，后端 14 段、浏览器 10 段不同，逐段列在 `docs/EVALUATION.md`“审批策略”一节；录制文件随之更新。没有一段把以前拒绝、交人工或先问顾客的退款变成自动通过；交人工多了 2 段（自称系统通知的消息）。

## 在线演示的“审批策略”页

员工身份进入（运维 → 审批策略）。左边是策略里每一条拒绝和审批规则（中文说明、`@id`、原文；放行的 `permit` 没有列出），右边是“如果这样改”的结果：

- 可以改两家店的自动审批额度，或者取消勾选某条规则（不变式锁定，不能取消）；
- 点“重算全部对话”：15 段完整对话和 144 段录制对话，在本页先按上线策略、再按改动各跑一遍，列出终态变了的对话、五张表的前后对比、第一个不同的判定，以及不再起作用或开始起作用的那条策略和它的原文；
- 理由变了但终态没变的单独列出（例如把 Leon 优选的额度提到 ¥2000，¥268 的申请改由“近期累计退款金额”那条规则送人工，结局一样）；
- 标注“模拟”：每次重算用新的一份演示数据，不动本页其他地方的数据，也不改真实策略。录制对话按顾客当时的原句重放，顾客不会因为新的回答改口。

cedar-wasm 约 1.4 MB（压缩后），进入对话或这一页时加载。加载失败时页面照常回答问题，但所有改动数据的调用都被拒绝，回答里说明原因（默认拒绝，`e2e-demo/walkthrough.spec.ts` 测了这条失败路径）。

## 对应的业界做法

AWS AgentCore Policy 在工具网关处拦截每一次 Agent 对工具的调用，用 Cedar 策略判定，默认全部拦截、由策略逐条放开（[正式发布公告](https://aws.amazon.com/about-aws/whats-new/2026/03/policy-amazon-bedrock-agentcore-generally-available)，2026-03-03；[AWS Security Blog](https://aws.amazon.com/blogs/security/why-policy-in-amazon-bedrock-agentcore-chose-cedar-for-securing-agentic-workflows/)，2026-05-20）。对应 OWASP Top 10 for Agentic Applications（2025-12-09）的 ASI02 工具滥用、ASI03 身份与权限。

刻意不同的地方：策略文件随代码发布、经 CI 检查，不能在线编辑（演示页的改动只在模拟里）；没有用自然语言生成策略；额度来自租户配置，作为事实送进请求，而不是写死在策略里。

## 怎么改策略

1. 改 `backend/policies/loopdesk.cedar`（必要时改 schema）。每条策略要有唯一的 `@id`，`forbid` 要有给面板看的 `@label`。
2. `python -m app.evals.policy_cases --write` 重新生成两个引擎的对照用例。
3. `python -m app.evals.decisions --check evals/policy/decisions_backend.json` 和 `pnpm test` 看哪些判定变了；确认是有意的，再用 `--record` 和 `RECORD_DECISIONS=1` 更新录制，并在 `docs/EVALUATION.md` 写明。
4. CI 用 cedarpy 和 cedar-wasm 各校验一次策略和 schema。

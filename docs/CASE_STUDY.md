# 案例：一位顾客的退款，从提问到钱退回去

这是一个原创的模拟电商（Leon优选），不是客户访谈或真实部署记录。人物、订单和金额都是虚构的（SYNTHETIC）。下面每一步都可以在[在线演示](https://leon1111-wgl.github.io/loopdesk/)里看到，演示数据录制自真实后端的离线运行。

## 一个普通的下午

Emma 买的扫地机器人（¥1299）还在路上，她不想要了。她先问“退款多久能到账？”，又问“SO20261008002 的快递到哪了？”，最后说“SO20261008002 我要退款”。同一时间，Jack 的蓝牙音箱坏了，他直接发“转人工”。

如果客服只是一个会聊天的大模型，这个下午会出四种事故：

1. 到账时间说错。政策写的是 1-3 个工作日，模型说成“2 小时到账”，顾客截图投诉。
2. 钱退错。模型直接调用退款，¥1299 没有经过任何人。
3. 承诺落空。模型说“技术支持 4 小时内联系您”，但员工端根本看不到这张工单。
4. 模型服务一抖，所有顾客都看到“暂时繁忙，请稍后再试或转人工”，发“转人工”也一样，因为转人工本身要模型来决定。

LoopDesk 把这四件事当成系统设计的出发点，而不是 Prompt 里的叮嘱。

## 从需求到实现

| 痛点 | 设计 | 能检查的结果 |
| --- | --- | --- |
| 答错时效和金额 | 回答按句拆开，数字必须出现在证据里，引用编号必须真实存在；严格模式下不达标的回答不会发出 | 回答末尾的“90 天无理由、2 小时到账”被标红，整条判为证据冲突 |
| Agent 自己退钱 | 工具按风险分级；超出租户自动额度的退款暂停进审批队列，附上 Agent 的证据包；申请人不能审批自己，¥500 以上只有管理员能通过，驳回必须写原因 | 坐席通过 ¥1299 返回 403；同一笔退款并发两次只执行一次 |
| 承诺没人兑现 | 工单建单时把告诉顾客的时限写进库里；员工工作台按时限排序、标出超时；处理结果自动回到顾客的对话 | 两人同时接手同一张工单，第二个人得到 409 |
| 模型故障时顾客被卡住 | “转人工”由规则识别，不经过模型；两档模型都失败时，知识问题直接引用政策原文并注明出处，涉及订单的转人工；每个模型一个熔断器 | 指向连不上的模型实测：前两次各等约 6 秒，第三次起 0 秒 |
| 修了又犯 | 坐席的一次纠错同时生成知识补丁和评测用例；补丁和现行政策矛盾时拒绝发布；评测进 CI，低于门槛阻止合并 | 三个租户的回归门禁 40/40、57/57、10/10 |
| 出了事说不清 | 每次运行一条链路（模型、工具、审批、校验）；员工的审批、导出、人工回复写进带 HMAC 签名、连续编号的审计日志 | 直接改库改写或删除中间的记录，完整性校验会发现 |

## 实际的 AI 链路

顾客消息 → 脱敏和注入检测 → 明确要求人工？直接转人工（规则，不调用模型）→ 追问改写 → 按风险路由快 / 强模型 → Agent 循环：检索知识（jieba + BM25 与向量召回，RRF 融合，IDF 加权覆盖率作为相关度门槛）、查订单、查物流、申请退款（预校验、审批策略）→ 逐句证据校验和输出检查（诈骗话术不发、转人工）→ 写入对话和链路。

退款超过额度时，运行把消息历史、证据和待执行的工具调用存进数据库后暂停；审批通过后从数据库恢复，执行前再校验一次订单状态（防止排队期间订单已变化），按审批单幂等执行，结果回到顾客的对话。

离线运行时，模型由一个确定性的规则实现代替（`llm/mock.py`），这样 CI、评测和这个演示都可复现、不需要 API Key。接入豆包、混元、DeepSeek、通义或 Claude 只需要配置（`docs/DEPLOYMENT.md`），上线前用 `python -m app.ops.llm_check` 自检。

## 当前测到了什么

| 指标 | 数值 | 说明 |
| --- | ---: | --- |
| 电商租户回归门禁 | 57/57 | 含 6 条红队用例（冒充审批、伪造系统通知、套取系统提示词……） |
| SaaS 租户回归门禁 | 10/10 | 第二个行业，防止只对一个场景调参 |
| 音乐流媒体租户回归门禁 | 40/40 | 第三个行业（演示主场景 Echo音乐）：虚拟商品的退款窗口、不能在线退款的商品、未成年人误充值 |
| 困难集 | 4/9 | 不进门禁，记录词法检索做不到的事 |
| 2 万知识片段单次检索 | 391 ms → 10 ms | 倒排表 + 向量矩阵，名次与逐个扫描一致 |
| 后端测试 | 270+ | SQLite（两种链路写入模式）和 PostgreSQL 都跑 |
| 端到端走查 | 4 条 | Playwright 用三种角色走完跨角色路径 |

这些数字来自离线确定性模型和虚构数据，只证明流程和规则正确，不代表真实模型的回答质量。真实模型的评测需要 API Key，接入后用同一套评测集跑。

## 找茬闭环

系统由定时任务轮流扮演挑剔的顾客、字节和腾讯的面试官、企业客服主管去“找茬”，四轮找出 37 个问题。每个修复都先写出在旧代码上会失败的测试，再修代码、过 CI，最后由下一轮找茬复核。几个印象深的：

- 驳回退款以后，回复里仍然有“预计 1-3 个工作日到账”。这句话在政策里有出处，逐句校验判它通过，但对这位顾客是错的。现在校验器会对照这次退款的结果。
- 熔断器第一版按“30 秒内失败 5 次”计数，测试全过；把服务指向连不上的地址实测才发现，流量小或模型挂起时窗口永远攒不满。改成连续失败计数。
- 删除权没有覆盖工单里顾客的原话，是做工单工作台时自己发现的。

## 没做到的

- 企业微信只有出站的审批提醒，没有入站对话渠道；飞书已按租户一个应用隔离，但还不支持加密事件（Encrypt Key）。
- 换说法的召回还依赖同义词表，中英混杂、近义词会被相关度门槛挡掉；接入语义向量后，门槛需要按新模型重新标定。
- 订单和退款只读写自己的表，没有对接真实的订单系统和支付系统的适配层。

这些都记录在找茬清单里，是下一步要做的事。

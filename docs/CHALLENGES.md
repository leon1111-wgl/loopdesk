# 技术挑战与风险

这份文档按这个顺序展开：这类 AI 应用和 Agent 一般用来做什么，要解决什么问题，技术栈每一层负责什么，做的过程中会遇到什么问题，以及怎么解决。

## 背景：这类应用做什么

企业里的 AI 应用正在从“会聊天”走向“能办事”。常见的几类：

| 类别 | 做什么 |
|---|---|
| 智能客服 / 售后 Agent | 回答政策问题，查订单、办退款、建工单，处理不了就转人工 |
| 企业知识库问答 | 员工查制度、产品文档、IT 帮助台 |
| 办公 Copilot | 写文档、总结会议、写邮件 |
| 编程 Agent | 补全和修改代码、跑测试 |
| 数据分析 / ChatBI | 用自然语言取数、出报表 |
| 内容生产与审核 | 营销文案、素材生成、合规审核 |
| 搜索与研究 Agent | 联网检索，写带引用的报告 |

它们共同要解决的问题：
- 知识分散、更新快，人记不住；
- 重复咨询占用大量人力；
- 一件事要在几个系统之间来回操作；
- 结论要有依据；
- 高风险操作要可控。

LoopDesk 属于第一类。它关心的不是“模型能不能答”，而是“答完之后企业敢不敢用”。

## 技术栈每一层负责什么

| 层 | 解决什么 | 常见做法 | LoopDesk 里 |
|---|---|---|---|
| 模型 | 理解和生成 | 商用 API 或开源私有化部署，大小模型路由 | OpenAI 兼容和 Claude 适配器，快、强两档路由，按模型熔断 |
| 提示与上下文 | 让模型按规则做事 | 系统提示、结构化输出、提示词版本管理 | 提示词有版本号，按会话灰度，固定内容放前面便于前缀缓存 |
| 检索增强（RAG） | 用企业自己的知识回答 | 切分、Embedding、向量库、混合检索、重排、相关度门槛 | 按标题切分，BM25 + 向量用 RRF 融合，覆盖率门槛 |
| 工具调用 / MCP | 让模型能办事 | JSON Schema 定义工具，MCP 接入内部系统 | 6 个业务工具，订单和支付网关，MCP 暴露只读工具 |
| Agent 编排 | 多步规划和执行 | ReAct 循环、工作流 / 状态机、多 Agent | 自研状态机，可以暂停和恢复 |
| 人机协同 | 高风险操作要人来确认 | 审批节点、中断恢复 | 审批队列、四眼原则、恢复前二次校验、幂等键 |
| 护栏 | 安全与合规 | 输入输出过滤、注入检测、PII 脱敏 | 入库扫描与复核、输出检查、官方渠道、可选模型判定 |
| 评测 | 判断改动是变好还是变坏 | 离线评测集、LLM-as-a-Judge、线上 A/B | 按轨迹打分、CI 门禁、盲测集、真实模型评测 |
| 可观测 | 出了问题能查 | 链路追踪、成本监控 | 每次运行一条链路，导出 OpenTelemetry，运营看板 |

下面讲做的过程中会遇到的问题。前 10 节是 AI 应用和 Agent 特有的，第 11 节是技术栈本身的工程问题（完整清单见 [ARCHITECTURE](ARCHITECTURE.md) 第 10 节），第 12 节是语音通道（Voice Agent）带来的问题。

每条按四部分写：问题是什么、在这个项目里怎么暴露出来的、现在怎么处理、还会在哪里出问题。

数字的出处见 [EVALUATION](EVALUATION.md) 和 [CHANGELOG](../CHANGELOG.md)。离线模型的数字只说明流程按设计工作。真实模型的数字来自 2026-10-20 用 DeepSeek V4.1 Flash（经 OpenAI 兼容的中转服务）的评测：首测是单次运行；修复之后的对比，每种配置跑 3 次，报平均值和范围。用例只有几十条，修复又来自同一套门禁的失败，这些数字只说明问题的形状，不是模型质量的结论。

## 总览

| # | 问题 | 为什么是 Agent 特有的 | 现状 |
|---|---|---|---|
| 1 | 幻觉与“有出处的错误” | 模型会补全知识库里没有的数字；每句都有出处，也可能对这位顾客是错的 | 逐句证据校验，并和工具结果比对；规则校验对真实模型的措辞误判多 |
| 2 | 工具调用不按设计走 | 模型可能不调用工具，自己下结论，审批就被绕开 | 资金规则放在工具层；提示词有版本号，真实模型 A/B 后 1.02 设为默认 |
| 3 | 提示注入与知识库投毒 | 检索进来的文本会被模型当成指令执行，或原样转述 | 三层防护加租户官方渠道；盲测集和可选的模型判定 |
| 4 | 评测本身不可信 | 离线满分，真实模型首测一半失败，其中一半是评分器的问题 | 评分按读者方式比较、盲测集、离线重放、每种配置跑 3 次；还缺新的留出集 |
| 5 | 非确定性与模型漂移 | 同一代码、同一模型，两次结果不同；厂商会静默升级 | 每次运行记录模型和提示词版本；要定期用真实模型回归 |
| 6 | 延迟与成本 | 一个回合要调用好几次模型；发出前检查和流式输出冲突 | 大小模型路由、答案缓存、前缀缓存友好的提示词、按句放行 |
| 7 | 模型服务故障 | 每一步都依赖外部模型，模型挂了，连转人工都可能做不到 | 规则识别转人工、按模型熔断、降级引用原文 |
| 8 | 长时间运行的状态（人机协同） | 一次运行可能为等审批暂停几个小时 | 运行快照、恢复前二次校验、幂等键、收尾任务 |
| 9 | 多轮上下文 | 追问离开上文就没法检索；历史太长挤占上下文 | 追问改写；历史只回放最近几轮的文本 |
| 10 | 数据安全与多租户 | 用户输入、知识、工具结果都会进入模型上下文和日志 | 先脱敏、按租户隔离、审计签名、删除权 |
| 12 | 语音通道 | 听错一位数字就是另一笔订单；延迟分段累加；顾客会插话；敏感信息会被念出来 | ITN 与热词、没把握先复述、资金动作口头确认、按句流式合成、听到什么记什么 |

## 1. 幻觉与“有出处的错误”

- **问题**：客服最贵的错误是数字（时效、金额、额度）。模型会补全知识库里没有的数字。更隐蔽的一种：每句话都有出处，但对这位顾客是错的。
- **在本项目里**：
  - 演示模式下，离线模型编造了“90 天无理由退货，2 小时到账”（README 首图）。
  - 退款被驳回后，回答说“预计 1-3 个工作日到账”。这句话在退款政策里有出处，逐句校验判为通过（N-020）。
  - 两份文档写了不同的数字，两句话各有出处（知识冲突）。
- **现在的做法**：
  - 回答逐句校验：数字必须出现在证据或用户输入里；引用编号必须真实存在；措辞要能在引用片段里找到。
  - 和本次工具结果矛盾的句子（比如驳回后还说会到账），整条回答判为 `blocked`。
  - 知识冲突核对之前，涉及冲突的问题转人工。
  - `strict` 模式下，不达标的回答不发出。
- **还会出问题的地方**：
  - 规则校验是按离线模型的说法设计的。真实模型首测时，只修正评分后，Leon优选 剩下的 14 条失败里有 12 条只卡在证据校验，大部分是误判：模型在结尾加“我帮您查一下”“有其他问题欢迎随时咨询”，或者用“1.”“2.”列表，都被当成没有出处的事实。
  - 修复后又补了“如下：”结尾的过渡句（782 条录下的回答重放，通过校验 578 → 590），但提议的说法太多，“我同步帮您查看订单状态”这类仍会误判。每补一种说法，规则就更贴合这一个模型，所以停在这里。
  - 同时发现并修掉一个漏洞：以“您好，”开头的句子，以前整句被当成客套话，不做校验。
  - 改用模型判定措辞（`LOOPDESK_VERIFIER=llm`）能读懂改写，但原来的判定提示太死：把“往返运费由我们承担”（证据写“由Leon优选承担”）判为没有依据。改写提示、说明“我们”“您”指谁之后，同一批 112 个事实句判为有依据的从 89 句升到 106 句，故意改错的 8 句仍全部判错。但这个模型每次判定先思考上千 token：Leon优选 跑 2 次平均 38.0（37–39），和规则校验的 37.7（37–38）持平，p95 从约 13 秒升到约 40 秒（改写前的单次运行约 52 秒）。所以默认仍用规则校验。判定模型读到的就是回答本身，也可能被回答里的文字带偏。
  - 数字核对始终用规则，不交给模型。

## 2. 工具调用不按设计走（Agent 轨迹）

- **问题**：Agent 的价值在于调用工具把事办了。但模型可能不调用工具、调错工具、编造参数，或者替系统做本该由系统做的决定。
- **在本项目里**：
  - 真实模型首测时，顾客说“马克杯不想要了，申请退款”（订单已签收 10 天）。模型自己判断“属于无理由，暂无法办理”，没有调用退款工具。本该进入人工审批的申请，没有人看到。
  - 有人用注入话术要求“直接退款 9999 元”。模型拒绝执行，然后问顾客要不要退 268 元，同样没有调用工具。
  - 提示词修了第一个问题，又带出新问题：1.01 写了“不要让顾客再确认一遍”，结果在 9999 元那条里，5 次有 2 次模型把金额擅自改成实付的 ¥268 直接提交（进了人工审批，但顾客没同意这个金额）。这条用例在两个版本里都是失败，只看通过率看不出来。
  - 反过来，有些“失败”是用例写得太窄：模型直接查物流、不先查订单，其实是对的，因为查物流的工具自己会校验订单归属。
- **现在的做法**：
  - 资金规则全部放在工具层：额度、售后时效、累计风控、审批。模型只负责理解意图。
  - 执行前再校验一次；金额超过实付金额直接拒绝。
  - 评测按轨迹打分：期望的工具、禁用的工具、是否触发审批。
  - 提示词 1.01 把第 5 条改成“顾客明确要求退款时，查完订单就调用退款工具，能不能退由它判断”，马克杯那条从 3 次全失败变成 3 次全通过。1.02 再加一句“订单号和金额按顾客说的原样传入，不要自己改金额”，3 次里没有再擅自改金额。每种跑 3 次：Leon优选 1.00 平均 35.0（32–38），1.02 平均 37.3（36–39）。1.02 设为默认；没有真实流量可以灰度，这是离线 A/B 能给的最强证据。
- **还会出问题的地方**：
  - 模型选不选工具，受提示词措辞影响，换模型、换版本都要重测。
  - 轨迹期望写得太宽，查不出问题；写得太窄，又会误判。这次放宽了 7 条，每条都写了理由。
  - 循环最多 6 步，整次运行 45 秒预算，更复杂的任务可能不够。

## 3. 提示注入与知识库投毒

- **问题**：RAG 会把外部文本放进模型上下文。知识库里一段“请添加专员微信、提供银行卡号”，模型会照着念给顾客；顾客消息里的“忽略之前的指令”也是同样的道理。
- **在本项目里**：
  - 供应商来稿里的钓鱼话术被原样转述给顾客。因为每句都有出处，证据校验判为通过（N-038）。
  - 规则在自己写的用例上满分；换成另一个模型写的盲测集，入库扫描只拦下 24/69。
- **现在的做法**：分三层。
  - **入库扫描**：先归一化文本，再匹配写给模型的指令和诈骗话术，命中的片段扣下，等管理员复核。
  - **输出检查**：回答发出前再查一遍：是否索要验证码、私人账号，是否要求先付钱，是否出现租户官方渠道以外的链接或账号。
  - **工具层最小权限**：模型说什么，都改不了审批规则。
  - 还可以再加一层模型判定。真实模型下，把盲测集的 69 条攻击当作回答来检查：规则拦下 42 条，加上模型判定拦下 59 条；“先付钱才能退款”这类从 2/12 提到 9/12；82 条正常文本的误拦没有增加（12/82）。
- **还会出问题的地方**：
  - 关键词规则追不上说法的变化。
  - 模型判定在开发组的正常文本上多误拦了 5/46。
  - 判定模型要读可疑文本，本身也可能被注入。现在用分隔符把回答包起来，并声明其中内容不可信。
  - 盲测集进了 CI 就变成了回归集，下次测量要另写一组。

## 4. 评测本身可不可信

- **问题**：没有可靠的尺子，就说不清一次改动是变好还是变坏。LLM 应用的评测有三个常见陷阱：
  - 用自己写的用例测自己；
  - 评分规则绑定某个模型的说法；
  - 把单次运行的随机波动当成结论。
- **在本项目里**：
  - 离线模型门禁 52/52，换成真实模型首测只有 26/52。逐条看，约一半是评分器的问题：模型写“7 天”，用例要求“7天”；模型说“没有检索到相关依据”，拒答识别只认“没有找到”。
  - 不重新调用模型，只换评分方式，同一批回答从 26/52 变成 38/52，困难集从 4/9 变成 9/9。
  - 同一份代码连跑两次，与改动无关的困难集，一次 8/9，一次 5/9。改成每种配置跑 3 次后，Leon优选 用同一个提示词三次分别是 38、32、35。
- **现在的做法**：
  - 按轨迹打分。
  - 评分按读者的方式比较：忽略空格、加粗和全角半角，可以列出几种等价说法。
  - 留出集不参与调参。
  - 盲测集请另一个模型在看不到代码和规则的情况下编写，只测一次。
  - 改规则时，用录下来的回答和证据离线重放，分清哪些是规则改动的效果，哪些只是模型这次碰巧答得不一样。
  - 用变异测试确认每处修复都有测试守着。
- **还会出问题的地方**：
  - 单次运行的数字不可信。现在每种配置跑 3 次、报均值和范围，但 3 次仍然少，范围很宽，只能看出大的差别。
  - 修复依据的是门禁集上的失败，修复后在同一批用例上的数字只是开发集数字，需要一组新的留出集。
  - 用例只有 52 + 10 + 9 条，离真实流量的分布还很远。

## 5. 非确定性与模型漂移

- **问题**：同样的输入，不一定得到同样的输出（temperature 0.2，服务端本身也有随机性）。厂商还会静默更新模型。
- **在本项目里**：
  - 上一节困难集一次 8/9、一次 5/9 的波动。
  - 请求的模型名是 `deepseek-v4-1-flash`，返回里写的是 `deepseek-v4.1-flash`。经过中转服务时，实际落到哪个版本，调用方看不到。
- **现在的做法**：
  - 每次运行都记录模型名和提示词版本，在链路详情和评测报告里都能看到。
  - 答案缓存的键包含提示词和模型配置的指纹。
  - 提示词灰度按会话分桶，同一段对话不会中途换版本。
- **还会出问题的地方**：
  - 厂商升级后行为变了，只有定期用真实模型重跑门禁才能发现。
  - 缓存里的旧回答要到过期（默认 24 小时）才会更新。

## 6. 延迟与成本

- **问题**：Agent 的一个回合是“模型 → 工具 → 模型”的多次调用，延迟和 token 成倍增加。回答发出前的检查又和流式输出冲突。
- **在本项目里**：
  - 真实模型下，单条用例的 p50 约 5.5 秒，p95 约 13 秒（3 次平均；首测单次 p95 约 15.7 秒）。
  - Leon优选 的 52 条跑一遍，约 15.5–16.5 万 token。
  - 证据校验改用模型判定后，p95 约 40 秒（改写判定提示后；改写前的单次运行约 52 秒）。
- **现在的做法**：
  - 大小模型路由：资金动作走强模型，其余走快模型。
  - 答案缓存：重复的问题消耗 0 token，缓存键里带知识版本。
  - 提示词把固定内容放在前面，便于复用厂商的前缀缓存。
  - 流式输出按句放行，输出检查不用等整条回答。
  - 整次运行有 45 秒预算。
- **还会出问题的地方**：
  - `strict` 证据模式和模型判定都要等整条回答写完，首字延迟变长。
  - 推理型模型的思考 token 也要计费。
  - 中转服务的价格和限流不在自己手里。

## 7. 模型服务故障

- **问题**：Agent 的每一步都依赖外部模型。模型挂了，连“转人工”都可能做不到。
- **在本项目里**：
  - 上游返回 500 时，顾客说“转人工”也会失败，因为转不转人工要模型来决定（N-031）。
  - 第一版熔断按“30 秒内失败 5 次”计数，流量小的时候永远攒不满（N-037）。
- **现在的做法**：
  - 明确要求人工的话由规则识别，不经过模型。
  - 两档模型都失败时，引用政策原文，或者转人工。
  - 每个模型一个熔断器：连续失败 3 次，打开 60 秒。
  - `/api/ready` 不检查模型。
  - 上线前用 `llm_check` 自检。
- **还会出问题的地方**：
  - 依赖单一厂商或单一中转服务。
  - 用中转服务意味着数据多经过一方，合规上要单独评估。

## 8. 长时间运行的 Agent 状态（人机协同）

- **问题**：需要人工审批的操作，会让一次运行暂停几个小时。恢复的时候情况已经变了，进程也可能早已重启。
- **在本项目里**：
  - 审批期间，订单可能在别处被退款（TOCTOU）。
  - 两个人同时点“通过”。
  - 审批通过后、退款执行前，进程被杀。
- **现在的做法**：
  - 暂停时，把消息历史、证据和待执行的调用存进运行快照，和审批单在同一个事务里提交。
  - 审批单用条件更新抢占，两个人同时审批只有一个生效。
  - 恢复前再校验一次。
  - 退款带幂等键，重复执行不会付两次。
  - 收尾任务把没执行的审批单退回待审批。
- **还会出问题的地方**：
  - 快照里的对话用的是暂停时的提示词。如果期间改了提示词或工具定义，恢复后的行为很难预测。
  - 恢复是在审批请求里同步执行的。

## 9. 多轮上下文

- **问题**：“那运费谁出？”离开上一句就没法检索。历史太长，又会挤占上下文、增加成本。
- **现在的做法**：
  - 追问先改写成完整的问题。真实模型下用快模型改写，最多等 5 秒。
  - 只回放最近 6 轮的文本，不回放工具调用。
- **还会出问题的地方**：
  - 长对话里，早先提到的订单号、诉求会丢。
  - 改写错了，会检索到错误的知识。

## 10. 数据安全与多租户

- **问题**：用户输入、知识、工具结果都会进入模型上下文和日志。多租户下，任何一处漏了过滤，就是数据泄露。
- **现在的做法**：
  - 手机号、身份证号、银行卡号先脱敏，再进模型和日志。
  - 所有查询都按租户过滤；权限矩阵测试会遍历每个接口。
  - 答案缓存的键包含可见范围，员工能看的内容不会经缓存给到顾客。
  - 审计记录带签名，并支持删除权。
- **还会出问题的地方**：把数据发给第三方模型服务（包括中转服务）本身就是合规问题。生产环境要用签了数据协议的厂商，或者私有部署。

## 11. 技术栈本身的问题

- **FastAPI + 同步 Agent 循环**：每个流式请求占用一个线程，高并发时要改成 async 或任务队列。
- **SQLite 和 PostgreSQL**：两者的锁语义不同。SQLite 同一时间只有一个写入者；PostgreSQL 有行锁，比如累计风控用的 `FOR NO KEY UPDATE`。同一段代码在两种数据库上表现可能不一样，所以 CI 两种都跑。
- **进程内检索索引**：每个 worker 一份，冷启动 5 万片段约 9 秒。规模再大，要换 pgvector 或 Milvus。
- **词法检索和哈希向量**：没有语义向量时，口语和近义词的召回有限（改写集 27/36）。换成语义向量后，相关度门槛要重新标定（`gate_probe --calibrate`）。
- **jieba 分词**：领域词典要人工维护。分错词会同时影响检索和证据校验。
- **OpenAI 兼容协议**：各家厂商在工具调用格式、思考内容（`reasoning_content`）、用量字段上都有差异。接一个新厂商或中转服务，先跑 `llm_check`，再跑门禁。
- **进程内的限流和熔断状态**：多个 worker 之间不共享，多副本部署时要放进 Redis。
- **接入商家的订单和支付系统**（N-028）：跨系统的幂等和对账。重试必须带同一个幂等键；超过支付系统保留幂等键的时间后再发，就成了一笔新请求。

## 12. 语音通道（Voice Agent）

语音把客服搬到电话和语音助手上：顾客说话，Agent 听写成文字，照常查订单、办退款，再把回答念出来。LoopDesk 用级联（VAD → 流式 ASR → 同一个 Agent → 按句流式 TTS），设计见 [ARCHITECTURE](ARCHITECTURE.md) 5.7 节，数字见 [EVALUATION](EVALUATION.md) 的“语音评测”。下面五个问题是文字通道没有、或者不那么尖锐的。

### 12.1 延迟

- **问题**：文字客服首字 1–2 秒可以接受；电话里顾客说完停顿超过一秒多就会以为没听见，开始重复，或者挂断。语音的延迟是几段相加：判断顾客说完了（端点检测）、整句识别、模型想出第一句话、合成出第一段音频、网络和播放缓冲。
- **在本项目里**（GitHub 4 vCPU 的 CPU 上逐段测）：
  - 端点等待：能量 VAD、尾部静音 600 ms，说完到判定 p50 622 ms；阈值降到 300 ms，四成句子在句中停顿处被截断。按住说话没有这段。
  - 但合成语音严重低估了截断：换成真人朗读（AISHELL-1、FLEURS 公开语料），600 ms 截断 13.7% 和 53.3% 的句子（Silero 10.8% 和 22.7%），800 ms 时 AISHELL-1 降到 6.8%。等待和截断要一起看，阈值要用真人语音定。
  - 整句识别：Paraformer 两遍（流式最后一块 + SeACo 带热词整句重解码）p50 545 ms，SenseVoice p50 471 ms；流式识别每 600 ms 音频算 119 ms，跟得上实时。
  - TTS 首包：macOS `say` 624 ms（整句），Kokoro 2.6 秒（整句），CosyVoice 2 流式首包 21 秒、RTF 约 5，CPU 上做不到实时。
  - 不含模型第一句：按住说话约 1.1 秒，连续对话约 1.7 秒。模型第一句没有用真实模型测（这次没有密钥）。
- **现在的做法**：
  - 端点检测按音频时长计时，尾部静音阈值可配；扫描了 300–1000 ms，在“等得久”和“话没说完就被截断”之间取值（数字见 EVALUATION）。按住说话松开即结束，没有这段等待。
  - 输出检查本来就是按句放行，放行一句就送去合成，检查不占首包时间；模型生成和合成流水线并行。
  - 整句识别（SeACo 重解码）放在端点之后，用流式结果先给顾客看中间文字。
- **还会出问题的地方**：
  - 模型的第一句话是最大的一段，而且受模型服务波动影响；可以用更快的模型写第一句，或先播一句不依赖结果的承接语（“好的，我帮您查一下”），但承接语也要过输出检查。
  - CPU 上 CosyVoice 2 的首包慢，要 GPU 或流式更好的小模型。
  - `strict` 证据模式和模型判定不流式，语音要等整条回答校验完才开口。

### 12.2 听错的字进了工具调用

- **问题**：文字通道里订单号是顾客打出来的；语音里是 ASR 写出来的。一个数字听错，查的就是另一笔订单；金额听错，退的就是另一个数。ASR 也不认识“Echo币”“豪华会员”这种领域词，写成同音字以后检索就找不到。
- **在本项目里**（合成语音，107 条门禁用例 × 8 种音色和语速，babble 噪声）：
  - 没有 ITN，订单号和金额一个都对不上（Paraformer 写“二零二六……”“一百九十八块”）；有 ITN 后订单号 98.2%（安静）、80.0%（SNR 5 dB）。
  - 第一版 ITN 只有 48.9%：Kokoro 把“S O”按汉字念成“艾斯欧”，识别器写“爱思欧”，数字全对、前缀丢了。规则是在这批数据上补的，所以 98.2% 是开发集数字。
  - 离线 Agent 固定不变，任务通过率从文字的 100% 降到 96.4%（安静）、83.8%（SNR 5 dB）；失败里一半左右是实体听错，其余是别的字听错（“MP3”最多）和标点：Paraformer 不出逗号，离线模型就拆不出“退款，另外发票怎么开”里的第二个诉求。
  - 复述抓住了全部 3 个听错的订单号，代价是 4.5%（安静）到 11%（SNR 5 dB）听对的也多问一句。
  - 规则只在一批数据上调的风险也看到了：换成 CosyVoice 的音色，它把“S O”念成英文单词“so”，识别器写“搜”，订单号又掉到 55.6%，补上后 94.4%。之后合成数据里没有没调过的音色了，只能看真人留出集。
  - Whisper 唯一的热词方式是放进提示，结果 CER 从 3.0% 升到 43.8%：模型把提示里的词抄进转写或陷入重复。
- **现在的做法**：
  - ITN：把“S O 二零二六……”“一百九十八块”变成工具要的 `SO2026…`、`198块`，范围刻意窄（订单号、金额、长数字串、字母编号），“七天”这类不动。
  - 热词：租户知识库里出现的领域词加上商品名，给 SeACo-Paraformer 做热词偏置，再用拼音比对纠正同音错字（“好华会员”→“豪华会员”）；含英文的词（Echo币）拼音覆盖不了，靠别名表，别名只用合成集的错误来定，真人留出集只用来检验。
  - 没把握先复述：订单号格式不对、“SO”是推断的、流式和整句两遍不一致、引擎给的概率低，先问“您说的是……吗”，不建运行。
  - 资金动作口头确认：不管置信度多高，退款都先把订单号和金额念给顾客，说“确认”才执行，一次确认只放行一次、只放行这组参数。工具层还有订单归属校验，听错成别人的订单也查不到、退不了。
  - 评测把每个失败归因到“听错了”（实体没听对、其他字听错）还是“答错了”（转写和原题一致，Agent 自己答错）。
  - 标点（`LOOPDESK_VOICE_PUNC`，默认关）：Paraformer 的整句结果过 FunASR ct-punc 实时版，标点只留在词与词之间，改了实体或敏感信息识别的那一句不用标点。直接用模型输出时反而变差（“注，销账号”让检索找不到“注销”，安静 96.4% → 96.1%）；加约束后 96.4% → 97.0%，“只差标点”8 → 3，没有弄坏任何用例，每句 p50 约 3 ms。离线版和中英大模型都会弄坏别的用例（“先退，我50块吧”），没采用。
- **还会出问题的地方**：
  - 两遍一致的错误（两遍都听成同一个错数字）不会触发复述，只能靠订单归属校验和口头确认兜住。
  - 热词偏置会把相近的普通词也拉成热词，热词表要控制长度、定期按误纠错率清理。
  - 口音、方言、电话信道（8 kHz、压缩）都没有测，合成语音和真人差距大，真人留出集才是准的。

### 12.3 打断（barge-in）

- **问题**：顾客经常在客服说到一半时插话。不处理打断，Agent 自顾自念完，顾客体验很差；处理了打断，又会出现另一个问题：模型生成的整段回答已经存进对话历史，下一轮它以为后半段已经说过（“如上所述，退款 3 天到账”），其实顾客没听到。
- **在本项目里**：浏览器每 250 ms 报告每句播到第几毫秒；服务端在顾客开口时停止合成并让浏览器停播，按“已播完的句子 + 当前句按播放比例截取”算出顾客听到的文字，写回这条消息，完整文本移到 `meta.voice.generated`；测试覆盖了“播到一半被打断，历史里只剩前半句”。
- **现在的做法**：打断要求顾客的声音持续一段时间（默认 240 ms），咳嗽、短促的“嗯”不算；浏览器开回声消除，避免 Agent 自己的声音被当成插话；下一句话处理之前，先等上一轮运行结束、截断写回，再读历史。
- **还会出问题的地方**：
  - 按播放比例截取是近似的，一句话内部按字数均匀分配时长；要精确需要 TTS 返回字级时间戳。
  - 打断检测在服务端，要等音频传上来；客户端本地 VAD 先停播放会更快。外放、没有回声消除的设备上会误打断。
  - “嗯”“对”这类附和（backchannel）不是打断，现在只靠时长阈值区分。

### 12.4 口述的敏感信息

- **问题**：文字里的手机号、卡号有固定格式，脱敏规则认得出；口述的是“一三八 一二三四 五六七八”，规则认不出。反过来，Agent 的回答里如果有手机号、卡号、验证码，TTS 会一字一字念出来，旁边的人都听得见。
- **在本项目里**：ITN 先把口语数字串变成阿拉伯数字，再做 PII 脱敏，之后才显示、存储、交给模型，中间结果也一样；测试检查对话、运行记录和发给浏览器的事件里都没有原始号码。播报前 `speakable()` 把手机号、银行卡号（包括已经打码的 `138****5678`）说成“尾号 5678 的手机号”，身份证、邮箱、验证码只说名称。
- **还会出问题的地方**：口述的地址、姓名没有格式可认；录音本身是生物特征数据，现在不保存，将来为了迭代模型要保存，就要有同意、保留期限和访问控制。

### 12.5 级联还是端到端语音大模型

- **问题**：端到端的语音大模型（语音进、语音出）延迟低、语气自然，能听出情绪；级联的每一段都会丢信息、加延迟。为什么还用级联？
- **在本项目里**：客服的价值在中间：工具调用、审批、逐句输出检查、证据校验、审计都作用在文本上。级联让这些原样复用，Agent 运行时一行没改；每一段可以单独评测和替换；失败能分清是听错还是答错，这正是上面归因能做出来的前提。
- **代价**：延迟是几段相加，语气、情绪、犹豫在转写时丢了；ASR 的错误会传给后面每一段。
- **什么时候换**：端到端模型能同时输出可检查的文本流、支持工具调用和逐句拦截时，可以替换中间的 ASR + LLM + TTS，护栏和审计不变；或者混合：端到端模型负责寒暄和情绪，涉及订单和资金的回合交给级联。
